# Поэтапное продолжение исправлений N2Q

Правила работы: один завершённый проверяемый этап — отдельный коммит; отчёт на
русском каждый час с SHA коммитов, проверками, проблемами и следующим шагом.
На этапах 0–7 создание расписания было заблокировано, локальная файловая
система была доступна только для чтения. После предоставления доступа
19.10.2026 почасовая автоматизация включена, локальная ветка синхронизирована,
репозиторий сделан приватным и main защищена. Подробности: [этап 8](stage-8-repository-access.ru.md).

## Этап 0 — исходное состояние и уточнение рисков

Проверен PR №1 и его ветка codex/security-hardening.
Исходный коммит: d545ad202f4b5e40e54e92d9e09c773ebfa3dc80.
Рабочая копия без изменений.

Дополнительная проверка FireLine в памяти, без записи на диск:
- штатная посылка успешно расшифровывается;
- та же посылка с дописанным неаутентифицированным хвостом также принимается;
- 300 случайных коротких входов не вызвали исключений Python.

Это ограниченная воспроизводимая проверка, не coverage-guided фаззинг.
По исходному коду C обнаружено, что n2q_fireline_open не принимает вместимость
выходного буфера, хотя пишет в него до проверки тега. Необходимо добавить
outcap и проверить граничные случаи с ASan/UBSan. Верификатор CoNe использует
общий static-буфер pk; конкурентную проверку следует сделать безопасной.

## Последующие этапы и критерии завершения

1. FireLine: ограничение выходного буфера C, строгие версии/схемы/число
   получателей, точный размер посылки, проверка длин до расшифрования,
   сохранение нулевой выходной длины при отказе. Регрессии Python/C и
   межъязыковая совместимость действительных посылок; отдельный коммит.
2. Фаззинг: управляемая мутация корректных N2QF/nqc/FireLine входов, корпуса,
   sanitizer-harness C и Rust cargo-fuzz, воспроизводимый запуск в CI.
   Отказ при повреждении, отсутствие падений/переполнений, сохранение KAT.
3. CoNe: исключить общий изменяемый буфер верификатора, определить безопасную
   выдачу одноразовых индексов и восстановление после сбоев, протестировать
   гонки, повтор индекса и откат. Защита от полного отката снимка требует
   внешнего доверенного состояния; локальный счётчик сам её не доказывает.
4. Бюджеты ресурсов и ключи: ограниченные параметры KDF, контролируемая память
   и входные длины, явные ошибки вместо panic/неограниченных выделений.
5. Потоковые файловые API: ограниченная память во всех поддерживаемых портах,
   целостность целого файла и атомарная публикация результата; межъязыковые
   проверки, пустые/многоблочные файлы, ошибки ввода-вывода.
6. Фронтенд и сборки: лимиты, отмена и очистка, отказ worker, заголовки
   тестового хостинга, проверка согласованного комплекта WASM/JS и браузерные
   негативные сценарии.
7. Подготовка к выпуску: воспроизводимые проверки и набор материалов для
   независимого криптоанализа, документация миграций и оставшихся рисков.
   Собственная проверка не считается независимой экспертизой и не
   подтверждает заявленную стойкость 128/256 бит.

Не сливать PR и не развёртывать сервис автоматически. Для каждого этапа
фиксировать реальный результат проверки; не объявлять этап завершённым при
блокировке записи, тестов или коммита.
