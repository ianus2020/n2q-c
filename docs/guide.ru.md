# N2Q-C — руководство разработчика

Практическая инструкция: как применять N2Q-C во всех сценариях, которые
поддерживает библиотека. Все сигнатуры взяты из реального кода репозитория.

> ⚠️ **Статус.** N2Q-C — исследовательский артефакт. Внешнего аудита **не было**.
> Заявленные уровни стойкости — цели дизайна, подтверждённые собственными
> измерениями. **Не защищайте им реальные секреты** до внешнего криптоанализа
> (этап M6). Для продакшена сегодня берите libsodium / AES-GCM / Ascon.

---

## 1. Базовые понятия

| Термин | Что это | На что влияет |
|---|---|---|
| **Ключ** | 16 байт (N2Q-128) или 32 байта (N2Q-256) | главный секрет; из CSPRNG или KDF |
| **Nonce** | 16 байт, «номер сообщения» | уникальность; в основном режиме повтор **не катастрофа** |
| **AAD** | данные, которые аутентифицированы, но не шифруются | связывает шифр с контекстом (id пользователя, RTP-заголовок) |
| **Профиль** | `SECURE` = 16 раундов, `FAST` = 8 раундов | запас прочности ↔ скорость (~2×) |
| **Комплект (suite)** | N2Q-128 или N2Q-256 | размер ключа и состояния; 256 — для пост-квантового запаса |
| **Токен** | `nqc.` + base64url | самоописывающий формат: профиль/комплект читаются автоматически |

**Ключевое свойство основного режима (SIV):** случайный повтор nonce раскрывает
лишь факт «два сообщения совпали», а не ключ и не поток. У AES-GCM/ChaCha та же
ошибка — полный провал.

### Золотые правила

1. **Ключ — из CSPRNG или KDF.** Никогда не хардкодьте (демо-ключи в примерах —
   только для тестов).
2. **Профиль/комплект должны совпадать** у отправителя и получателя — либо
   используйте токен, который сообщает их сам.
3. **AAD — это контекст.** Если зашифровали с `AAD="user:42"`, расшифровать
   получится только с тем же AAD. Используйте это, чтобы шифр нельзя было
   «переставить» в чужую запись.
4. **Проверяйте результат.** Расшифровка возвращает `None`/`false`/исключение —
   это не мелочь, а сигнал подделки. Никогда не используйте данные до проверки.
5. **256 бит — если данные должны пережить квантовый компьютер.**

## 2. Быстрый старт

```bash
# 1. Получить исходники
git clone https://github.com/ianus2020/n2q-c && cd n2q-c

# 2. Убедиться, что порт совпадает с эталоном (должно быть ALL PASS)
cd impl/python && python3 test_kat.py
cd ../go        && go run .
cd ../c         && cc -O2 n2qc.c -o n2qc && ./n2qc
cd ../n2q-c-ref && cargo test
```

`ALL PASS` означает: ваша сборка бит-в-бит совпадает с эталоном.

### Первое шифрование

<details open><summary><b>Python</b></summary>

```python
import n2qc, os

key   = os.urandom(16)                 # 16 байт = N2Q-128
nonce = os.urandom(16)

tok = n2qc.seal_token(128, n2qc.FAST, key, nonce, b"ctx", b"секрет")
pt  = n2qc.open_token(128, key, b"ctx", tok)      # b"секрет"
```
</details>

<details><summary><b>Go</b></summary>

```go
tok := n2qc.SealToken(n2qc.Fast, key, nonce, []byte("ctx"), []byte("секрет"))

```
</details>

<details><summary><b>Rust</b></summary>

```rust
use n2q_c_ref::modes::{capsule, Profile};

let tok = capsule::seal128(Profile::Fast, &key, &nonce, b"ctx", b"secret");
```

</details>



## 3. Каталог сценариев

Ниже — все поддерживаемые сценарии. Для каждого: зачем, API и подводные камни.

### 3.1. Шифрование поля / сообщения (базовый режим)

**Когда:** любое «спрятать данные» — поле в БД, сообщение, конфиг.

| Язык | API |
|---|---|
| Python | `seal(bits, profile, key, nonce, ad, pt)` → `sealed`; `open(...)` → `None` при подделке |
| Go | `Seal(profile, key, nonce, ad, pt)`; `Open(...) ([]byte, bool)` |
| Rust | `n128::seal(p, &key, &nonce, ad, pt)`; `n128::open(...) -> Option` |
| C | `seal_128(key, nonce, ad, adlen, pt, ptlen, out, rounds)` |
| PHP | `n2q_seal($profile,$key,$nonce,$ad,$pt)`; `n2q_open(...)` → `null` при провале |
| Swift | `seal(profile, key, nonce, ad, pt)`; `openN2Q(...) -> [UInt8]?` |

**Совет:** храните результат как **токен** (`seal_token`/`SealToken`/`capsule::seal128`),
тогда получателю не нужно знать профиль — он записан в токене.

**Подводный камень:** `sealed` — это `тег(16) ‖ шифртекст`. Не обрезайте его.

### 3.2. Поиск по зашифрованным данным (blind index)

**Когда:** нужно найти строку по e-mail/телефону, не расшифровывая таблицу.

```python
bi = n2qc.blind_index(128, n2qc.SECURE, key, b"alice@x.com")
# кладём bi рядом с шифртекстом; поиск:  SELECT * FROM t WHERE bi = ?
```
Go: `BlindIndex(Secure, key, value)` · Rust: `n128::blind_index(p, &key, value)` ·
PHP: `n2q_blind_index(N2Q_SECURE, $key, $v)` · Swift: `blindIndex(SECURE, key, v)`

**Подводные камни:**
- Blind index **детерминирован** — одинаковый вход даёт одинаковый индекс. Это и
  даёт поиск, и раскрывает **равенство** значений (частотный анализ по
  низкоэнтропийным полям вроде «пол» — плохая идея).
- Работает только на **точное совпадение**. Диапазоны (`BETWEEN`) не
  поддерживаются намеренно (см. §5, ORE).
- Индексируйте нормализованное значение (`lower(trim(email))`), иначе поиск
  промахнётся.

### 3.3. Пароли → ключ (Balloon KDF)

**Когда:** ключ выводится из пароля пользователя.

```rust
use n2q_c_ref::pw;
let key32 = pw::derive(password, salt, s_cost, t_cost);   // [u8; 32]
```

**Подводные камни:** соль — уникальная на пользователя, ≥16 байт, хранится
открыто. `s_cost`/`t_cost` подбирайте так, чтобы вывод занимал ~100–500 мс на
вашем железе. Пароль **никогда** не используйте как ключ напрямую.

### 3.4. Файлы любого формата (контейнер N2QF)

**Когда:** документы, фото, архивы, видео — «зашифровать файл».

| Язык | API |
|---|---|
| Python | `encrypt_file(bits, profile, key, in, out)` / `decrypt_file(bits, key, in, out)` |
| Go | `EncryptFile(profile, key, in, out) error` / `DecryptFile(key, in, out) error` |
| Rust | `file::encrypt_file(profile, &key, in, out)` / `file::decrypt_file(&key, in, out)` |
| C | `enc_file(profile, key, bits, in, out)` / `dec_file(key, in, out)` |
| PHP | `n2q_encrypt_file($profile,$key,$in,$out)` / `n2q_decrypt_file($key,$in,$out)` |
| Swift | `encryptFile(profile, key, in, out)` / `decryptFile(key, in, out)` |

Формат: `"N2QF" | ver | suite | { le32(len) | sealed }*`, блок 64 КБ,
оверхед ≈ **0.07 %**. Профиль и комплект пишутся в заголовок → при расшифровке
передавать их не нужно.

**Проверено:** файл, зашифрованный на одном языке, открывается на всех
остальных (Python ↔ Rust ↔ Go ↔ C ↔ Swift, побайтово).

### 3.5. Перемотка зашифрованного медиа (seekable)

**Когда:** плеер должен прыгнуть на середину зашифрованного видео.

```python
cont = m.n2qf_build(key, [chunk0, chunk1, chunk2])
data = m.seek_chunk(key, cont, 1)        # только нужный блок
```
Go: `SeekChunk(key, buf, index)` · Rust: `seek_chunk(&key, &buf, i)` ·
C: `n2q_seek_chunk(key, buf, buflen, index, out, &outlen)`

**Подводный камень:** индекс — номер **блока**, а не байтовое смещение.
Позиция в секундах → номер блока считает ваш контейнер/плеер.

### 3.6. Реальное время: звонки, видео, игры (streaming)

**Когда:** поток пакетов, где потери и перестановка — норма.

```python
tx, rx = m.StreamTx(key), m.StreamRx(key)
pkt = tx.seal(b"rtp-header", frame)        # 1 пакет = 1 токен, +24 байта
out = rx.open(b"rtp-header", pkt)          # None → отбросить пакет
```
Go: `NewStreamTx/NewStreamRx`, `.Seal/.Open` · Rust: `StreamTx::new/.seal`,
`StreamRx::new/.open` · C: `n2q_stream_init/_seal/_open` (см. `n2q_stream.h`).

Свойства: nonce = номер пакета (в заголовке), **скользящее окно анти-реплея на
64 пакета**, номер аутентифицирован (подмена ловится), битый пакет отбрасывается
локально — поток идёт дальше.

**Подводные камни:** состояние `Rx` — на одного отправителя (не переиспользуйте
один объект для разных пиров); для минимальной задержки берите `FAST`.

### 3.7. Forward secrecy: захват устройства не раскрывает прошлое (ратчет)

**Когда:** мессенджеры, звонки, всё «переписку нельзя прочитать задним числом».

```python
tx, rx = m.RatchetTx(root), m.RatchetRx(root)   # root — общий 16-байтовый корень
pkt = tx.seal(b"hdr", b"сообщение")
out = rx.open(b"hdr", pkt)
```
Go: `NewRatchetTx/NewRatchetRx` · Rust: `RatchetTx::new/RatchetRx::new` ·
C: `n2q_ratchet_tx_init/_rx_init/_seal/_open`.

Как работает: ключ каждого пакета выводится из цепочки, цепочка **перематывается
односторонне и старое значение стирается**. Пропущенные ключи кэшируются (окно
64) — поэтому перестановка и потери допустимы; использованный ключ стирается,
значит реплей тоже невозможен.

**Подводные камни:**
- Расшифровка **необратимо меняет состояние** — храните его аккуратно; откат
  бэкапа сломает канал.
- `root` должен попасть обеим сторонам безопасно (сегодня — вне библиотеки;
  см. `connect.md`).

### 3.8. Ротация ключей без перешифрования (envelope)

**Когда:** есть терабайты данных, надо сменить мастер-ключ.

```python
blob = m.wrap(kek1, dek)               # маленький «конверт» рядом с данными
dek  = m.unwrap(kek1, blob)
blob = m.rewrap(kek1, kek2, blob)      # ротация: данные не тронуты
```
Go: `Wrap/Unwrap/Rewrap` · Rust: `wrap/unwrap/rewrap` · C: `n2q_wrap/_unwrap/_rewrap`.

Схема: данные шифруются **один раз** под `dek`; `dek` обёрнут под `kek`. Ротация
переписывает только конверт (десятки байт).

**Подводный камень:** `dek` — на объект/арендатора, а не один на всё; иначе
компрометация одного `dek` вскрывает всё.

### 3.9. Дедупликация зашифрованного хранилища (convergent)

**Когда:** бэкапы/облако, где одинаковые файлы не должны занимать место дважды.

```python
dek, ct = m.conv_seal(master_key, content)   # одинаковый контент → одинаковый ct
data    = m.conv_open(dek, ct)
```

**Подводный камень (важный):** режим **детерминирован by design** — это и даёт
дедуп, и позволяет тому, у кого есть тот же `master_key`, проверить «есть ли у
вас вот этот файл». Ключ `master_key` — на арендатора, чтобы посторонний такую
проверку сделать не мог.

### 3.10. Скрытие длины сообщения (length-hiding)

**Когда:** приватные мессенджеры, где размер выдаёт содержимое.

```python
tok = m.seal_padded(key, nonce, b"", pt, bucket=256)
pt  = m.open_padded(key, nonce, b"", tok)
```
Go: `SealPadded(..., bucket)` / `OpenPadded` · Rust: `seal_padded/open_padded`
· C: `n2q_seal_padded/_open_padded`.

Длина шифра раскрывает только «корзину». Больше корзина — лучше приватность,
больше трафика.

### 3.11. Журнал, где видна любая правка (audit-log)

**Когда:** комплаенс, supply-chain, аудит-трейлы.

```python
head = m.log_genesis()
rec, head = m.log_append(head, seq, key, b"user alice login")
ok = m.log_verify(key, [rec, ...], head)     # False при правке/реордере/удалении
```
Go: `LogGenesis/LogAppend/LogVerify` · Rust: то же · C: `n2q_log_init/_append/_verify`.

**Подводный камень:** ценность даёт **хранение `head` в доверенном месте**
(другой сервис, подпись, публикация). Если атакующий может переписать и записи,
и `head`, — цепочка ничего не докажет.

### 3.12. Жалоба на злоупотребление в E2E (franking)

**Когда:** мессенджер, где получатель должен доказать модератору содержание —
не раскрывая ключ и чужую переписку.

```python
tok = m.frank_seal(key, nonce, msg)                 # отправитель
msg, cf, opening = m.frank_open(key, nonce, tok)    # получатель
ok = m.frank_report_verify(cf, opening, msg)        # модератор: без ключа!
```

**Подводный камень:** модератор проверяет только то, что ему **добровольно**
раскрыли (`msg`, `opening`). Подставить другое сообщение получатель не может
(binding), но он может и **не** сообщать — это и есть баланс приватности.

### 3.13. Обход DPI / цензуры (stego) — **опционально**

**Когда:** трафик не должен опознаваться по сигнатуре.

```python
blob = m.stego_seal(key, nonce, b"", pt)   # nonce(16)|sealed — без заголовка
pt   = m.stego_open(key, b"", blob)
```

Обычный токен начинается с `nqc.` — это отпечаток. Stego его убирает: выход
неотличим от случайных байт (проверено chi-square).

**Подводные камни:**
- **По умолчанию не включён** — включает разработчик осознанно.
- Комплект и профиль **не** записаны в данные: стороны договариваются заранее.
- Прячется полезная нагрузка; хендшейк, размеры и тайминги — задача транспорта.

### 3.14. Шифрование с сохранением формата (FPE) — **опционально**

**Когда:** legacy-БД, где колонка обязана остаться 16-значным номером.

```python
ct = m.fpe_encrypt(key, b"tweak", "4111111111111111")   # → другой 16-значный
pt = m.fpe_decrypt(key, b"tweak", ct)
```
Go: `FpeEncrypt/FpeDecrypt` · Rust: `fpe_encrypt/fpe_decrypt` · C: `n2q_fpe_encrypt/_decrypt`.

Конструкция — **FF1** (NIST SP 800-38G, 10-раундовый Фейстель), раунд-функция =
наш PRF. Свой FPE мы не изобретали.

**Подводные камни:**
- Малые домены (4-значный PIN = 10 000 вариантов) — это **токенизация**, а не
  сильное шифрование.
- `tweak` (например, id счёта) разделяет домены — используйте его.
- Нативные порты (Python/Go/Rust) согласованы между собой, но **не** байт-в-байт
  с C-модулем `n2q_fpe.c` (другой домен MAC).

### 3.15. Шифротекст, привязанный к ключу (key-committing)

**Когда:** если ключ может быть подобран/подставлен (пароли, мультиарендность).

```python
tok = m.seal_committing(key, nonce, ad, pt)
pt  = m.open_committing(key, nonce, ad, tok)     # None, если ключ «чужой»
```

Даёт иммунитет к **partitioning-oracle** атакам, которые ломают AES-GCM/ChaCha.
Цена: +32 байта.

### 3.16. Пост-квантовый выбор

Ничего включать не надо — просто **используйте N2Q-256** (ключ 32 байта):
классические 256 бит → ~128 бит против Grover. Подробности:
[post-quantum.md](post-quantum.md).

### 3.17. Совместимость между языками

Все реализации сверены по общим KAT-векторам
([impl/conformance/vectors.txt](../impl/conformance/vectors.txt)). Проверено:
файл N2QF и все расширенные режимы, созданные на одном языке, открываются на
других.

**Чтобы совместимость сохранялась:** не меняйте порядок полей, доменные байты и
раскладку — при своём порте сверяйтесь с векторами (см. [conformance.md](conformance.md)).

## 4. Выбор профиля и комплекта

| Задача | Комплект | Профиль |
|---|---|---|
| Большие медиа, реальное время | 128 или 256 | `FAST` |
| Хранение чувствительных данных | 128/256 | `SECURE` |
| Долгоживущие секреты, PQ-риск | **256** | `SECURE` |
| Встраиваемое, экономия | 128 | `FAST` |

Профили **взаимно читаемы**: токен сам сообщает, каким он сделан.

## 5. Чего библиотека НЕ делает

- **Не согласовывает ключи между чужими сторонами.** Симметрика требует общего
  ключа. Обмен между независимыми «центрами шифрования» — задача отдельного
  слоя (KEM + реестр), см. **[connect.md](connect.md)**. Не изобретайте
  самодельный обмен ключами.
- **Не скрывает метаданные** (кто-кому-когда) — нужен транспортный слой.
- **Не поддерживает диапазонные запросы** по шифру (ORE) — сознательно: такие
  схемы имеют доказанные утечки.
- **Не заменяет TLS** — это шифрование данных, а не канала.

## 6. Обработка ошибок

| Язык | Признак провала |
|---|---|
| Python | `None` (у `decrypt_file` — исключение `ValueError`) |
| Go | второй результат `ok == false` |
| Rust | `Option::None` |
| C | `0` / отрицательный код |
| PHP | `null` |
| Swift | `nil` |

Любой провал означает одно из: неверный ключ, неверный AAD, повреждение,
подделка, реплей. **Никогда** не отдавайте пользователю данные, полученные до
успешной проверки, и не раскрывайте в сообщении об ошибке причину.

## 7. Перед запуском (чек-лист)

- [ ] Self-test/KAT вашего порта печатает `ALL PASS`.
- [ ] Ключи из CSPRNG или KDF; в коде нет хардкода.
- [ ] Есть план ротации (см. 3.8) и хранения ключей.
- [ ] AAD связывает шифр с контекстом записи.
- [ ] Все ветки «расшифровка не удалась» обработаны и логируются.
- [ ] Выбор 128/256 и `FAST`/`SECURE` обоснован (см. §4).
- [ ] Помните: **до внешнего аудита — только пилоты, не реальные секреты**.
