# Этап 5 — потоковые файловые API

Rust, Go, PHP и Swift больше не загружают весь файл и не накапливают
целый результат перед записью. Вместе с уже потоковыми C/Python все шесть
файловых API используют блоки до 65536 байт, проверяют длину записи до
чтения/расшифрования и обрабатывают EOF отдельно от усечённого ввода.
Память ограничена несколькими буферами блока и внутренними буферами AEAD;
конкретный RSS зависит от runtime, аллокатора и потоков.

Расшифрованные блоки попадают только в закрытый временный файл (0600) в
каталоге назначения. Публичное имя меняется после финального тега, проверки
физического EOF, завершения записи и sync. При нормальной ошибке старый
выход сохраняется, временный файл удаляется. Сбой/убийство процесса может
оставить временный файл; это не secure erase. Утечки дискового места, длительность
и число одновременных заданий должны отдельно ограничиваться приложением.
Не заявляется гарантия сохранности при физическом отключении питания.

Обрабатываются короткие чтения/записи и ошибки IO. Счётчики idx/total проверяются
на переполнение; PHP использует безопасный предел PHP_INT_MAX. Формат N2QF v2,
поддерживаемые размеры ключей и параметры CLI не менялись.
Rust build/parse и Go in-memory/seek helpers по-прежнему собирают данные в RAM:
это явно документированные удобные API, не потоковые API для неограниченных
загрузок. Внутренние decrypt-to-staging helpers не публикуются как API
для выдачи неполностью проверенного файла.

Проверки: Rust/Go короткие чтения, ошибки источника/выхода, поздний хвост,
отказ staging с сохранением старого результата; PHP/Swift ограниченные чтения,
усечение, очистка staging; существующая матрица шести writer/reader портов
на пустых и многоблочных файлах, повреждения и 256-bit C/Go/Python.
Полное исполнение выполняется CI; локальный read-only режим позволяет
синтаксические проверки и подготовку исходников в памяти.
